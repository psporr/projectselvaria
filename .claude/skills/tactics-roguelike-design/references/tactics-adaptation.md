# Translating Roguelike Design to Grid-Tactics Squad Games

Every reference game in this skill (Slay the Spire, Hades, Darkest Dungeon) is built around **one character or one deck** as the unit of "build identity." A grid-tactics game's unit of build identity is a **squad** — several units, each with position, class, and equipment, acting together on a battlefield. That difference changes how almost every mechanic in this skill should actually be implemented. This file is the bridge; read the other reference files for the underlying principle, and this one for how to land it in a squad-tactics game specifically. Read alongside `tactical-rpg-design`'s own reference files (especially `map-and-encounter-design.md` and `classes-and-progression.md`) — this skill covers the run wrapped *around* combat, that one covers combat itself.

## Permadeath means something different with a squad

A single-character roguelike's permadeath is binary: the run ends the instant the character dies. A squad's permadeath is **partial and gradual** — losing one unit out of six is a real, material loss (a build slot, a role, possibly a favorite named character) without necessarily ending the run. This is a genuinely different tension than single-hero permadeath, and it's worth designing for on purpose rather than treating a fallen squad member as a lesser version of "you died":

- **Losing a unit should cost something concrete**, not just a stat total — a lost tank changes what formations are safe, a lost healer changes how much risk the squad can absorb going forward. If losing any one unit doesn't change how the player has to *play*, the loss isn't landing as a tactical event, just a numbers penalty.
- **Decide explicitly whether a fallen unit can return.** Full permadeath (gone for the run, maybe gone forever) is the classic-FE emotional target: tension and loss-aversion, and it only works if the player believes it (no take-backs). A softer model — revivable via a rare, opt-in mechanic (a specific relic/blessing, a rest-site-style choice, limited uses) — turns "a unit died" into its own risk/reward decision (spend a scarce resource to bring them back, or accept the loss and adapt) rather than a hard stop. Both are legitimate; a run that *claims* permadeath tension but quietly always lets you undo it isn't earning either effect.
- **A run's whole squad dying (a wipe) is this genre's equivalent of single-character death** — that's the actual run-ending event to design reward/meta-progression framing around (see `meta-progression.md`'s "failing forward"), not any individual unit falling.

## "Draft a card/relic/boon" maps onto several different things

A squad game has more than one kind of "choice moment" available, where a single-hero game really only has "improve my one build":

- **A blessing/relic pick** (Selvaria's existing model) maps closely to Hades' boons — a post-encounter buff choice. The lesson from `build-variety-and-choice-design.md` applies directly: make these class/role/positional-conditional rather than flat "+N to everyone," since a squad gives you a synergy axis (which units benefit) that a single-hero boon pool doesn't have.
- **Recruiting a new unit mid-run** is a squad-specific draft moment with no single-hero equivalent — it's simultaneously a build choice (what role/class do I need) and a risk decision (a fresh, low-level recruit is initially a liability). Treat new-recruit offers with the same "not an auto-include" scrutiny as a relic pool: a recruit that's strictly better than what you have isn't a choice, it's an upgrade with a menu screen.
- **Equipment/item drops** map onto Slay the Spire's card rewards most directly — same principles (avoid strict upgrades, favor build-shaping over flat stat items, let rarity track power without making low-rarity items feel like filler) apply near-verbatim.
- **Which unit to bring on a given encounter**, if not the full squad is required every time, is itself a draft-like decision unique to squad games — deciding a loadout of units for an encounter, from a larger recruited pool, is a legitimate additional layer of pre-encounter strategy with no single-hero analog at all.

## A "room" is a battle map, and that changes the room-design math

In a single-hero action roguelike, a "room" is a small, quick combat arena — content cost per room is relatively low, so a large room pool is affordable. A tactics "room" is a full battle map with its own terrain, objective, and enemy composition — much more expensive to hand-author well, and much more noticeable to a player if it's generic or unbalanced (see `procedural-vs-handcrafted.md`: this raises the stakes on "hand-author the content, proceduralize the selection" even further, since each piece of content costs more).

Practical implications:
- **A smaller, high-quality map pool, reused across runs with varied enemy composition and reward context, is usually the right tradeoff** over trying to build (or worse, procedurally generate) a unique map per encounter. The same map with a different enemy squad, different terrain-based objective, or different modifier already reads as a distinct encounter to most players — you don't need a fresh layout every time to avoid staleness.
- **Encounter "types" (from `run-structure.md`'s room grammar) translate concretely**: a Monster room is a standard battle on a standard map; an Elite room is a harder enemy composition (not necessarily a different map) with a better guaranteed reward; a Rest/Shop room can be a genuinely non-combat map screen (no battle at all this beat); an Event can be a text/dialogue choice with a squad-wide consequence, no map needed.
- **Turn-based pacing means you can afford richer choice UI than a real-time game can.** Since there's no clock pressure mid-decision, lean into detailed comparison tooltips, forecast panels, and explicit numeric readouts at choice moments (much like `tactical-rpg-design`'s own `ui-ux-conventions.md` forecast-panel guidance) — a player evaluating a relic/blessing pick in a turn-based game can and should get more information than Hades' real-time boon-pickup flow affords, since there's no cost to them reading it carefully.

## Difficulty scaling has a squad-specific lever the reference games don't

Single-hero difficulty scaling is almost entirely "make enemies tankier/harder-hitting" (Slay the Spire's floor tables, Hades' Heat modifiers). A squad-tactics game has an extra axis: **enemy count and composition variety**, independent of raising any single enemy's stats. Scaling primarily through "more enemies, more varied compositions" rather than "the same handful of enemies but bullet-sponges" tends to read as fairer and more interesting in a tactics game, since it changes the *tactical problem* (how do I handle being outnumbered, flanked, or facing a composition I haven't seen) rather than just making a fight take longer. This is worth deliberately favoring over pure stat-scaling when tuning an endless or long-finite run's curve.
